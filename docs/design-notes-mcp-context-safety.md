# 设计笔记：MCP 上下文安全与会话级存储

> **日期**：2026-08-28 · **性质**：产品/技术设计决策的实践沉淀（对应方针 D22/D23、技术方案 T39/T40）
> **来源**：实机使用中 AI agent 反馈的真实问题驱动的三条设计决策

## 一、会话级存储 vs 碎片存储——为什么粒度决定幻觉率

**背景**：用户问"这跟 claude-mem 有什么区别"。答案不在功能列表，在存储粒度。

| | 碎片式（claude-mem 等） | 会话级（SessionRelay） |
| -- | ---------------------- | --------------------- |
| 存储单位 | 压缩摘要片段，跨会话打散 | 完整会话（标题/时间线/来源/状态/决策） |
| AI 看到的 | "你之前说过…"（缺上下文） | "根据 8-28 ZCode《数据库选型》#12" |
| 幻觉机制 | 上下文污染 + 压缩失真 + 无法溯源 | 出处强制 + 按需查询 + 原文可回跳 |

**三个反幻觉架构承诺**：

1. **出处强制**（D10）：AI 回答必须带"哪个会话/哪条消息/哪个 agent"——有源可查
2. **按需查询**（pull）：AI 不问就不查 → 上下文干净，不被无关记忆污染
3. **原文可回跳**：AI 拿到原始对话全文，不是压缩摘要——决策的"为什么"完整保留

**推论**：压缩摘要丢上下文是幻觉的温床。AI 拿到"决定用 JWT"但不知道为什么、对比了什么、谁说的 → 凭想象补全 → 幻觉。我们的方案是让 AI 能拿到**原始对话**。

## 二、上下文安全护栏——不信任 AI 的自觉，用默认值兜底

**背景**：用户担心"AI 调 MCP 拿回大量内容导致上下文爆炸"。实测确认：`get_session_detail` 不加限制时，一个 230 条会话最坏可返回 ~920KB，足以吃掉 25% 的 Claude 上下文窗口。

**三道护栏**（D22）：

| 护栏 | 默认值 | 怎么工作 |
| ---- | ------ | -------- |
| 消息条数上限 | **20 条** | 不指定 end_msg 时最多返回 20 条 |
| 单条截断 | **1000 字** | 默认低于旧版 4000；需全文显式传大值 |
| 硬性总量 | **50KB** | 逐条累积字节，超 50KB 停止添加并标记 truncated |

**设计原则**：**默认安全，要更多需显式要求**。AI 拿到 `truncated: true` + `hint` 字段知道有更多、怎么拿——不是把门关上，是把门改成带指示牌的走廊。

**AI 懒得翻页的风险**：hint 字段不只说"有更多"，而是给出具体行动建议（`role="user"` / `get_decisions()` / `start_msg` 翻页），引导 agent 做正确的事。

## 三、渐进披露漏斗——存储量与上下文负载解耦

**背景**：用户问"存这么多，AI 一下检索到大量内容对吗"。答案：存量 ≠ AI 看到的量。

```
第一步  search_sessions("数据库")
        ↓ 10 条 × snippet 100 字 ≈ 2KB
        ↓ AI 扫 snippet，锁定 1-2 个相关的

第二步  get_session_detail(id, role="user", max_chars=1000)
        ↓ 只拉用户提问 ≈ 2KB

第三步  （仅在需要时）翻页或拉更大范围
```

**大多数场景走专用工具，不碰全文**：

| AI 想知道 | 该用 | 大小 |
| ---------- | ---- | ---- |
| "为什么决定用 X？" | `get_decisions()` | ~1KB |
| "这个文件怎么改的？" | `get_file_history()` | ~2KB |
| "还有什么没定？" | `get_unresolved()` | ~1KB |
| "用户问了什么？" | `get_session_detail(role='user')` | ~2KB |
| "完整讨论经过？" | 分页拉取（唯一重操作） | 分页控制 |

## 四、role 过滤——堵住 agent 逃逸出口

**背景**：实测中 AI agent 发现 `get_session_detail` 无法只拉用户提问（user + assistant 混合返回），于是**绕过 MCP 直接查 SQLite**。这绕过了 Scope 过滤、隐私边界、出处强制——整个安全模型被旁路。

**解法**：`get_session_detail` 增加 `role: 'user' | 'assistant'` 可选参数。

**深层教训**：当 agent 发现 MCP 工具面有洞时，它不会等着你补——它会自己绕过去。**工具面的完整性是安全边界的一部分**，不是便利功能。

## 五、文件内容不存入库——"为什么"归会话，"是什么"归 git

**背景**：用户问"AI 修改的文件里面的内容有必要存进去吗"。

**不存，理由**：

1. **文件系统是代码的事实源**——git 已追踪每次改动，我们再存一份是冗余
2. **对话的价值是"为什么"而非"是什么"**——AI 修改文件时通常解释为什么，这个解释在 `type='text'` 里已存
3. **存文件内容会让库膨胀 10-100 倍**
4. **`files_mentioned` 已记"哪些文件被讨论过"**——供 `get_file_history` 查，不需要存文件内容本身

**例外**：AI 在对话中贴了代码片段并解释（type='text' 含代码块）→ 已存，因为它是有上下文的代码讨论。
